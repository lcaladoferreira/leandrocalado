The actual risk surface

The model is not your authority boundary.

A language model can explain a failed pipeline, draft SQL, propose a contract and suggest a fix. None of that establishes that it should be allowed to change production. The harness decides which tools exist, which identity invokes them, what context enters the run, which policies apply, what evidence is required, whether execution may begin, and how the system stops or rolls back.

Production autonomy budget

Autonomy is a policy decision, not a confidence score.

The book develops a production autonomy model in which action is constrained by blast radius, sensitivity, reversibility, validation coverage, financial impact and criticality. The model can recommend. The harness decides what happens next.

01

Execute

Bounded, reversible action with sufficient evidence and policy coverage.

02

Prepare for approval

The agent prepares an exact, reviewable change; an accountable approval controls promotion.

03

Recommend only

Reasoning is useful, but control capacity is insufficient for direct execution.

04

Deny

The capability, scope or risk level falls outside the authorized production envelope.

The running case

One request. Many hidden production decisions.

The book repeatedly tests its architecture against a payment-company request: “Create a daily Data Product of transactions aggregated by merchant for the commercial team.”

Business ambiguity

Authorization, capture, settlement or reversal? Merchant legal entity or outlet? Which timezone, cutoff and correction policy?

Governance ambiguity

Which fields can the commercial team see? What must remain outside the agent context? What privileges exist in production?

Data correctness

A query can compile and still double revenue through a one-to-many join or use the wrong event timestamp.

Operational safety

Before promotion: cost, lineage, blast radius, test evidence, approvals and rollback must all be explicit.

FAQ

Questions a skeptical architecture review will ask.

Is this an Agent Bricks manual?

No. The book is about the surrounding runtime and control system: tools, identity, authorization, context, policy, contracts, verification, approvals, recovery, observability and operating evidence. Databricks capabilities are used as implementation substrate where appropriate.

Is this another prompt-engineering book?

No. One of its central distinctions is that instructions shape behavior while controls constrain behavior. A prompt can request restraint; an authorization boundary can make an unsafe action impossible.

Will the material age when APIs change?

Some product names and APIs will evolve. The book explicitly uses an August 2026 technology baseline and separates durable control-plane ideas from vendor-specific implementation details.

Does the book advocate maximum autonomy?

No. It argues for minimum necessary agency and bounded autonomy. Stable rules belong in deterministic code and workflows; agents are used where ambiguity and synthesis justify the additional variance and evaluation surface.

What is the core architectural idea?

Model → Agent → Harness → Data Platform → Business Outcome. The model reasons. The harness governs when that reasoning can become an action and what evidence must exist before, during and after execution.
